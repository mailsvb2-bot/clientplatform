# Аудит tenant-модели импортированного runtime

**Дата:** 2026-07-28  
**Baseline:** `e3336cf9f75e07f6a62296929e11b5358a10dde6`  
**Статус:** подтверждённый аудит кода перед первой мультитенантной миграцией

## Вывод

Импортированный runtime надёжен как однопродуктовый бот, но его идентичность и данные в основном привязаны к `user_id`. Для ClientPlatform этого недостаточно и небезопасно: один Telegram-пользователь может владеть несколькими бизнесами, работать в чужом бизнесе и одновременно быть клиентом третьего.

Поэтому механическое добавление `business_id` в отдельные handlers запрещено. Сначала вводится независимая серверная граница `Business` + `BusinessMember` + `TenantContext`, после чего каждый предметный модуль переводится на неё по одному вертикальному сценарию.

## Подтверждённые риски

### 1. `users` моделирует клиента одного продукта

`services/db/schema/_parts/part_01.py` создаёт `users(user_id PRIMARY KEY, work_time, home_time, work_index, home_index, demo_uses...)`.

Это профиль клиента ClientPlatform, а не нейтральная идентичность участника ClientPlatform. Владелец бизнеса, сотрудник и конечный клиент не разделены.

### 2. События не имеют tenant scope

Таблица `events` содержит `user_id`, тип события и metadata, но не `business_id`. При использовании такой таблицы для нескольких специалистов отчёт может смешивать одинаковые действия разных бизнесов.

### 3. Фоновые задачи не имеют tenant scope

Таблица `jobs` содержит `user_id`, `job_type`, время и payload, но не обязательный `business_id`. Job невозможно безопасно маршрутизировать в конкретный бизнес только по Telegram ID.

### 4. Идемпотентность разделена только по пользователю

`services/schema_core.py` создаёт `idempotency(user_id, key)` и `deliveries(user_id, kind, stage, scheduled_at)`. Для ClientPlatform ключ обязан включать бизнес-контекст, иначе одинаковые сценарии двух бизнесов одного человека могут блокировать друг друга или ошибочно считаться уже выполненными.

### 5. Администраторы глобальны

`config/settings.py` читает `ADMIN_ID/ADMIN_IDS` из окружения. Этот механизм допустим только как платформенный emergency/super-admin contour. Он не может быть моделью администраторов каждого подключённого бизнеса.

### 6. Канальные токены глобальны

Текущие `BOT_TOKEN`, `MAX_BOT_TOKEN`, `VK_GROUP_TOKEN` являются настройками одного deployment. Для будущего парка персональных ботов требуется `Connection/ManagedBot` с `business_id` и `credential_reference`.

## Принятое решение

На первом шаге старые таблицы не изменяются и не заполняются фиктивным `business_id`.

Добавляются:

- `businesses`;
- `business_members`;
- доменные роли и статусы;
- неизменяемый `TenantContext`;
- repository, который всегда проверяет активный бизнес и членство;
- запрет customer-роли в `BusinessMember`;
- защита последнего активного owner;
- cross-tenant regression wall.

## Почему additive migration лучше массового ALTER

- сохраняет поведение импортированного production-кода;
- не требует придумывать владельца для исторических записей;
- позволяет доказать tenant boundary до переноса денег, jobs и сообщений;
- оставляет rollback простым;
- снижает риск скрытого смешивания данных.

## Следующие обязательные миграции

1. Универсальная идентичность `User` отдельно от legacy-профиля клиента.
2. `Customer` и `CustomerIdentity` с составной уникальностью внутри бизнеса.
3. Tenant-scoped `Event` и аналитика.
4. Tenant-scoped jobs/outbox/idempotency.
5. `Connection` и `ManagedBot` с защищёнными credentials.
6. Перевод первого вертикального сценария: бизнес → программа → клиент → выдача → прогресс.

## Stop condition

Запрещено подключать второго реального специалиста, пока автоматические тесты не доказывают, что бизнес А не может читать, изменять, исполнять job или получать отчёт бизнеса Б.
