# ADR-0003: Program, Delivery и Progress — разные состояния

**Статус:** принято  
**Дата:** 2026-07-28

## Контекст

Первый сквозной сценарий ClientPlatform должен позволить специалисту создать программу, добавить уроки, подключить клиента, выдать материал и видеть прохождение. Модель выдачи должна оставаться универсальной и поддерживать аудио, видео, текст, документы, изображения, ссылки, задания и смешанные уроки без привязки к одному виду бизнеса.

Критически важно не смешивать:

- структуру программы;
- участие клиента;
- попытку технической отправки;
- фактический прогресс клиента.

## Решение

### Program и Lesson

- программа создаётся как `draft`;
- уроки можно добавлять только в draft-программу;
- публикация требует минимум один активный урок;
- после публикации структура первой версии программы неизменяема;
- уроки имеют уникальную положительную позицию внутри программы;
- поддерживаются `audio`, `video`, `text`, `document`, `image`, `link`, `task`, `mixed`.

### Enrollment

- клиент подключается только к активной программе;
- клиент должен быть активен в том же бизнесе;
- одна пара `(business, program, customer)` имеет одно enrollment;
- повторный запрос на подключение идемпотентно возвращает существующее enrollment;
- отменённое enrollment не перезапускается молча;
- завершённое enrollment не создаёт новую выдачу.

### LessonDelivery

`LessonDelivery` — техническая попытка передать конкретный урок клиенту.

Состояния:

```text
pending -> sent
pending -> failed -> sent
pending/failed -> cancelled
```

Инварианты:

- один delivery на `(business, enrollment, lesson)`;
- отдельный idempotency key включает enrollment и lesson;
- повторная отметка уже отправленного delivery не увеличивает attempts;
- network failure не меняет progress на completed;
- cancelled delivery нельзя отправить.

### LessonProgress

`LessonProgress` — прохождение урока клиентом.

Состояния:

```text
pending -> delivered -> opened -> completed
                           \-> skipped
```

В первом вертикальном сценарии реализованы `pending`, `delivered`, `completed`; `opened` и `skipped` зарезервированы схемой для следующих интерфейсов.

### Автоматическое продвижение

- enrollment создаёт pending delivery первого активного урока;
- успешная отправка переводит progress в `delivered`;
- завершение доставленного урока создаёт delivery следующего урока;
- повторное завершение не создаёт дубликат;
- завершение последнего урока переводит enrollment в `completed`;
- урок до успешной доставки завершить нельзя.

## Изоляция на уровне БД

Каждая таблица содержит `business_id`.

Составные внешние ключи доказывают одновременно:

- enrollment и customer принадлежат одному бизнесу;
- enrollment и program принадлежат одному бизнесу;
- delivery/progress относятся к уроку той же программы, что enrollment;
- нельзя подставить урок другой программы даже внутри одного бизнеса;
- нельзя связать delivery с объектом другого специалиста.

## Полномочия

- программы создают и публикуют `owner`, `administrator`, `manager`, `content_manager`;
- enrollment, delivery и progress управляют `owner`, `administrator`, `manager`, `support`;
- marketer и analyst не получают клиентский delivery contour;
- каждое действие повторно разрешает актуальный `TenantContext`.

## Идемпотентность

Ключ доставки:

```text
enrollment:{enrollment_id}:lesson:{lesson_id}
```

Уникальность действует внутри `business_id`. Дополнительно БД запрещает второй delivery для той же пары enrollment/lesson.

## Рассмотренные варианты

### Одна таблица «прогресс» с флагом отправки

Отклонено. Сетевые повторы, ошибки API и пользовательское прохождение имеют разные жизненные циклы.

### Создавать все delivery сразу при enrollment

Отклонено для MVP. Это усложняет паузы, динамическое расписание и отмену. Следующий урок планируется после завершения предыдущего.

### Изменять опубликованную программу на месте

Отклонено для первого контура. Это делает непонятным, какую версию проходят уже подключённые клиенты. Позже добавляется явное versioning/clone workflow.

## Последствия

### Положительные

- сетевой retry не искажает прогресс;
- повторные команды не создают дубликаты;
- программа универсальна для разных профессий и форматов;
- сквозной сценарий восстанавливается после перезапуска из БД;
- tenant и program isolation защищены constraints, а не только Python-кодом.

### Отрицательные

- больше таблиц и состояний;
- редактирование активной программы пока требует новой версии;
- transport worker и реальные канальные адаптеры подключаются следующим слоем;
- пауза, отмена и расписание по задержкам требуют отдельных use cases.

## Privacy

- `programs` и `lessons` сохраняются как контент бизнеса;
- `enrollments`, `lesson_deliveries`, `lesson_progress` имеют customer relation и зарегистрированы как `anonymize`;
- любая новая таблица с `business_id` остаётся fail-closed до явной политики.

## Проверки

- draft нельзя выдать клиенту;
- пустую программу нельзя опубликовать;
- уроки упорядочены и не добавляются после публикации;
- enrollment создаёт первый delivery ровно один раз;
- failed delivery можно повторить;
- delivery и progress не смешиваются;
- следующий урок создаётся ровно один раз;
- последний урок завершает enrollment;
- другой бизнес не видит программу/enrollment;
- DB отклоняет урок другой программы;
- privacy manifest покрывает весь вертикальный контур.
