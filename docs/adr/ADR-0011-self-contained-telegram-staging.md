# ADR-0011: Self-contained real Telegram staging

## Status

Accepted — 2026-07-28.

## Context

ADR-0010 introduced a secure media gateway and a manual real Telegram staging workflow, but the first operational form still required several external resources before one message could be proven end-to-end:

- a deployed public HTTPS gateway;
- a private filesystem or S3 object;
- a persistent media signing key;
- gateway URL and media reference variables;
- Telegram bot token and chat ID.

That dependency set was disproportionate for a staging smoke and made the most important provider proof easy to postpone indefinitely. At the same time, a raw bot token cannot be generated by repository code or GitHub Actions: Telegram issues it through `@BotFather`, and it must remain outside the repository.

## Decision

The manual `clientplatform Telegram Staging` workflow is self-contained except for one dedicated staging bot token.

During one bounded GitHub Actions job it:

1. creates a deterministic valid MP3 fixture;
2. generates an ephemeral HMAC signing key;
3. starts the real clientplatform filesystem media gateway on loopback;
4. downloads one pinned official `cloudflared` binary and verifies SHA-256;
5. exposes the loopback gateway through a temporary Cloudflare Quick Tunnel;
6. discovers a unique private Telegram `/start` through `getWebhookInfo` and `getUpdates` when chat ID is not explicitly configured;
7. probes the signed media URL with a byte range;
8. performs a real Telegram `sendAudio`;
9. terminates the gateway and tunnel and uploads non-secret diagnostics.

The required GitHub Environment secret is only:

```text
CLIENTPLATFORM_STAGING_TELEGRAM_BOT_TOKEN
```

`CLIENTPLATFORM_STAGING_TELEGRAM_CHAT_ID` is optional and resolves ambiguity when more than one private account has sent `/start`.

## Security properties

- The staging bot must be separate from ClientPlatform and all production projects.
- The bot token is never accepted through a workflow input and never written to artifacts.
- The signing key exists only for one workflow run and is masked by GitHub Actions.
- The media fixture and gateway exist only in the runner temporary directory.
- The gateway binds only to `127.0.0.1`; Cloudflare Tunnel establishes an outbound connection.
- `cloudflared` is pinned to version `2026.7.3` and the official Linux AMD64 SHA-256.
- The tunnel URL is temporary and is not persisted as product configuration.
- Chat discovery fails closed when a webhook is active, no private `/start` exists, or several chat IDs are found.
- Provider descriptions, token-bearing URLs and signed media URLs are not uploaded as diagnostics.

## Consequences

### Positive

- A real external Telegram delivery no longer depends on a separately deployed server, domain, object store or signing secret.
- The workflow proves that Telegram can fetch bytes from the actual clientplatform gateway implementation.
- The remaining manual prerequisite is explicit and irreducible: create a dedicated staging bot, store its token, and send `/start`.
- The same workflow can be rerun without permanent staging infrastructure or cleanup debt.

### Negative

- Cloudflare Quick Tunnels have no SLA and can be temporarily unavailable.
- The workflow is unsuitable for load, longevity, production readiness or stable endpoint testing.
- A new dedicated staging bot still requires one human action through Telegram's official BotFather flow.
- Auto-discovery requires the staging bot to have no webhook; a bot with webhook must use an explicit chat ID or a separate bot.

## Rejected alternatives

### Reuse an existing ClientPlatform bot token

Rejected because it violates clientplatform isolation and could send staging content to production users.

### Pass the token as a workflow input

Rejected because workflow inputs are not a secret-storage boundary and can be exposed in run metadata.

### Keep a permanent public staging gateway only for smoke tests

Rejected as unnecessary infrastructure, cost and operational surface before the product needs persistent staging.

### Upload media directly to Telegram as multipart

Rejected for this smoke because it would bypass the signed media gateway contract that this stage is intended to prove.

### Use an unpinned tunnel installer

Rejected because mutable install scripts and unverified binaries weaken the supply-chain boundary.

## Production boundary

This ADR does not authorize Cloudflare Quick Tunnel for production. Production still requires a stable HTTPS endpoint, controlled reverse proxy, private object storage, persistent secret management, readiness monitoring and operational ownership described in the media gateway runbook.
