# ADR-0001: Явный TenantContext и additive tenant boundary

**Статус:** принято  
**Дата:** 2026-07-28

## Контекст

Импортированный runtime использует `user_id` как главный ключ пользователя, событий, jobs, прогресса, выдачи и идемпотентности. В ClientPlatform один человек может иметь несколько ролей в нескольких бизнесах. Telegram ID не определяет бизнес однозначно.

## Рассмотренные варианты

### A. Глобальный `current_business_id`

Отклонено. Контекст легко протекает между callback, coroutine, worker и scheduler. Это прямо запрещено каноном.

### B. Добавить `business_id` во все legacy-таблицы одним большим ALTER

Отклонено на первом этапе. Для исторических данных нет честного business owner, а массовая миграция одновременно затронет платежи, jobs, аналитику и выдачу.

### C. Создать новую tenant boundary рядом с legacy-моделью

Выбрано. Новые `Business`, `BusinessMember` и `TenantContext` вводятся аддитивно. Legacy-поведение не меняется, а новые clientplatform use cases с первого дня обязаны принимать серверно разрешённый контекст.

## Решение

1. `businesses.id` и `business_members.id` — UUID в текстовом представлении, генерируемые сервером.
2. `BusinessMember` содержит только staff-роли. `customer` моделируется отдельной сущностью, а не членством в бизнесе.
3. `TenantContext` неизменяем и содержит `business_id`, `user_id`, `membership_id`, `role`.
4. Контекст разрешается только запросом к активным `businesses` и `business_members`.
5. Клиентский `business_id` никогда не считается доказательством доступа.
6. Каждая мутация повторно проверяет членство, чтобы отозванный сотрудник терял доступ немедленно.
7. Последний активный owner нельзя отозвать или понизить до другой роли.
8. Изменения состава владельцев сериализуются transaction-scoped блокировкой строки `businesses`, чтобы параллельные операции не оставили бизнес без owner.
9. Administrator не может назначать owner/administrator и изменять их членство.
10. Старые таблицы не получают фиктивный tenant scope.
11. `businesses` и `business_members` имеют явные privacy-manifest policies; новые персональные таблицы остаются fail-closed до регистрации политики.

## Последствия

### Положительные

- появляется доказуемая граница данных;
- один пользователь может безопасно работать в нескольких бизнесах;
- будущие repository/use cases получают единый контракт;
- миграция legacy-модулей выполняется постепенно;
- откат не требует восстановления старых таблиц;
- конкурентные изменения владельцев сериализуются на уровне БД.

### Отрицательные

- некоторое время существуют legacy- и clientplatform-модели параллельно;
- новые функции нельзя строить напрямую на старых `users/events/jobs`;
- потребуется последовательная миграция каждого вертикального сценария;
- membership mutation выполняет дополнительную блокирующую запись в строку бизнеса.

## Риски

- разработчик может обойти канонический clientplatform repository и обратиться к legacy-таблице;
- stale context может существовать в памяти;
- новые бизнес-объекты могут случайно получить lookup только по ID;
- длительная транзакция изменения сотрудников может задерживать другую mutation того же бизнеса.

## Снижение рисков

- мутации повторно разрешают actor membership;
- application layer импортирует repository только через `clientplatform.infrastructure`;
- `TenantContext.assert_business()` блокирует чужой объект;
- CI запускает cross-tenant regression tests;
- последующие repository обязаны принимать `TenantContext`, а не произвольный `business_id`;
- блокировка охватывает только короткую транзакцию изменения членства;
- code review проверяет отсутствие глобального tenant state.

## План миграции

1. Ввести tenant foundation и тесты.
2. Добавить универсальные Customer/Program сущности.
3. Перенести один полный вертикальный сценарий.
4. Добавить tenant-scoped events/jobs/idempotency.
5. Только после доказанного сценария отключать соответствующие legacy-пути.

## Проверки

- создание бизнеса атомарно создаёт owner membership;
- один user имеет два независимых context;
- член бизнеса А не получает доступ к Б;
- revoke действует при следующем запросе;
- administrator не повышает права;
- customer не сохраняется как BusinessMember;
- последний owner нельзя отозвать;
- последнего owner нельзя понизить;
- после назначения второго owner первого можно безопасно понизить.
