# ADR-0012: свободный паспорт деятельности и подключаемые рабочие модули

**Статус:** принято

## Контекст

Первый пользовательский Telegram-сценарий ClientPlatform не должен считать, что каждый специалист обязательно продаёт программы. Один человек консультирует, другой оказывает услуги, третий выдаёт курсы и материалы, а четвёртый совмещает несколько форматов или использует пока неизвестную платформе модель работы.

Жёсткий справочник профессий или один `business_type` быстро превратил бы продукт в набор исключений. Он также заставил бы владельца подгонять свою деятельность под терминологию системы.

## Решение

1. Владелец пишет описание деятельности свободным текстом. ClientPlatform не выводит юридические, профессиональные или коммерческие факты из этого текста автоматически.
2. Описание хранится в tenant-scoped `business_profiles` отдельно от технических возможностей.
3. Рабочие возможности подключаются как `business_capabilities` через стабильный connector registry.
4. Первая поставка содержит четыре connector key:
   - `programs` — специализированная существующая модель Program/Lesson/Delivery;
   - `consultations` — предложения консультаций;
   - `services` — предложения услуг;
   - `custom` — собственный формат с названием владельца.
5. Консультации, услуги и собственные форматы используют общий tenant-scoped слой `business_offerings`. Специализированные будущие модули могут получить собственные таблицы и application service, не меняя профиль бизнеса.
6. Клиент подключается по короткоживущей одноразовой ссылке. В БД хранится только SHA-256 токена; сырой bearer token существует только в ссылке владельца.
7. Telegram control mode включается только явным `CLIENTPLATFORM_CONTROL_BOT_ENABLED=1`. При выключенном флаге унаследованные handlers и поведение остаются прежними.
8. Включённый control mode использует уже загруженный `BOT_TOKEN`, зеркалируя его только в namespace `CLIENTPLATFORM_SECRET_CONTROL_TELEGRAM_BOT_TOKEN` в памяти процесса. Сырой токен не сохраняется в tenant tables.
9. Dispatch runtime автоматически включается в control mode, если оператор явно не задал `CLIENTPLATFORM_DISPATCH_RUNTIME_ENABLED`.

## Расширение

Новый пользовательский модуль добавляется как connector descriptor с постоянным ключом, названием, объяснением и маршрутом интерфейса. Универсальные форматы могут сразу использовать `business_offerings`; сложные форматы подключают собственный домен, сохраняя общие tenant, RBAC, audit, customer и connection boundaries.

Это не plugin execution из непроверенного кода. Connector registry остаётся доверенной серверной конфигурацией и не принимает исполняемый код от пользователя.

## Безопасность и изоляция

- каждый профиль, capability, offering и invite содержит `business_id`;
- доступ повторно разрешается через активный `BusinessMember` для каждой операции;
- callback не является авторизацией: `business_id` проверяется сервером;
- customer invite одноразовый, ограничен сроком и не может быть повторно использован другим Telegram-пользователем;
- raw Telegram token не записывается в `connections`, где хранится только secret reference;
- существующий ClientPlatform privacy manifest fail-closed покрывает все новые business-scoped таблицы.

## Проверки

- произвольное описание деятельности без готового списка профессий;
- несколько модулей одного бизнеса;
- собственное название custom-модуля;
- общий offering layer для консультаций и услуг;
- запрет offering для специализированного programs connector;
- cross-business invisibility;
- hash-only customer invite и one-user replay idempotency;
- отказ повторного использования invite другим пользователем;
- atomic one-lesson program creation;
- real dispatch materialization через shared Telegram bot reference;
- callback UUID compact encoding до лимита Telegram;
- control router раньше legacy `/start`, но полностью выключен по умолчанию.
