# ADR-0014: Клиентский прогресс программ

## Статус

Принято.

## Контекст

Канонический вертикальный сценарий ClientPlatform требует, чтобы специалист выдал клиенту программу, клиент получил материалы, а специалист видел прохождение. До этого изменения система создавала Enrollment, отправляла первый материал через dispatch outbox и показывала владельцу только агрегаты доставки. У подключённого клиента не было интерфейса для просмотра программ и фиксации выполнения.

Нельзя решать задачу доверяя `business_id`, `customer_id`, `enrollment_id` или `lesson_id` из Telegram callback. Также нельзя создавать отдельный scheduler или отдельный поток доставки для каждого клиента.

## Рассмотренные варианты

### 1. Только показывать отправленные сообщения

Плюсы: минимальный код.

Минусы: сообщение не является доказательством прохождения; владелец не видит прогресс; обязательный сценарий канона остаётся незавершённым.

### 2. Хранить прогресс в FSM Telegram

Плюсы: быстрый интерфейс.

Минусы: состояние теряется, не является tenant-safe источником истины, плохо переживает рестарт и не подходит нескольким каналам.

### 3. Использовать существующие Enrollment, LessonDelivery, LessonProgress и dispatch outbox

Плюсы: один источник истины, восстановление после рестарта, идемпотентность, совместимость с будущими managed bots, Mini App, VK и MAX.

Минусы: требуется отдельный customer-authorized application/repository слой.

## Решение

Выбран вариант 3.

- Telegram principal сначала разрешается в активную `CustomerIdentity` внутри указанного бизнеса.
- Все чтения дополнительно ограничены `business_id + customer_id`.
- Callback содержит компактные UUID-токены бизнеса и Enrollment, но сервер заново проверяет принадлежность.
- Урок завершается по позиции только после серверного поиска урока внутри Enrollment.
- Допустимы только состояния прогресса `delivered` и `opened`.
- Повторное завершение идемпотентно.
- Следующий `LessonDelivery`, `LessonProgress` и dispatch outbox создаются в одной транзакции.
- Уникальные ограничения и `ON CONFLICT DO NOTHING` защищают от двойного нажатия и конкурентных запросов.
- Последний урок переводит Enrollment в `completed`.
- Владелец видит клиент, программу, количество завершённых уроков и процент выполнения только после live membership/RBAC проверки.

## Последствия

Положительные:

- завершён обязательный путь «выдать программу → пройти → увидеть прогресс»;
- прогресс переживает рестарт;
- следующий материал использует уже подтверждённый connection/identity route;
- нет отдельного scheduler на клиента;
- модель готова для Mini App и дополнительных каналов.

Ограничения:

- ранний MVP использует явную кнопку «Готово», а не автоматическое определение фактического прослушивания;
- отправка следующего материала остаётся асинхронной через общий dispatch worker;
- редактирование многоурочных программ в Telegram будет отдельным сценарием.

## Риски и защита

- Подмена callback: блокируется повторным customer scope lookup.
- Cross-tenant доступ: запросы требуют одновременно business и customer scope.
- Двойное нажатие: блокируется state transition и уникальными ключами.
- Потеря маршрута доставки: следующий урок не создаётся, если прежний active connection/customer identity route нельзя подтвердить.
- Частичный commit: application use case использует одну DB-транзакцию.

## Проверки

- клиент видит только свои программы;
- чужой Telegram principal не читает и не завершает Enrollment;
- одноурочная программа завершается;
- многоурочная программа ставит следующий материал ровно один раз;
- повторный callback не создаёт дубль;
- владелец видит именной tenant-scoped прогресс;
- callback data укладывается в лимит Telegram 64 байта;
- полный CI, PostgreSQL, security и release gates обязательны перед merge.
